# 第二客户 Productization Review 与决策日志

**证据级别：两个客户、全部虚构。** Stage 7 的 Pilot 和 Stage 8 的启航工单均为模拟；原稿中“两家真实客户”“4 天首个 Demo”和现场 Failure 是待学习的叙事，不是本仓库已证明的商业结果。此文作为 60 分钟复盘参考答案。

| 候选能力 | 语义与重复证据 | 决定 | 尚欠证据 |
|---|---|---|---|
| WorkItem / Extraction Runtime | 邮件与工单都需要来源、租户、解析与结构化结果 | Core，Domain 保留强类型 Schema | 真正电话/微信转写与第三客户 |
| Context 接口 | 两者按实体取相关历史，但对象和冲突语义不同 | 共享 EntityRef/Request/Record；Adapter 留 Domain | 海川旧接口迁移、并发和授权 |
| Knowledge / Rule 执行 | 两者有版本/状态/Owner、有限条件动作 | 共享过滤与执行，语料/字段/政策留 Domain/Tenant | 真实文档签核和冲突治理 |
| Recommendation | 都是下一步建议，但 option 可是 SKU 或诊断行动 | 共享有类型契约，排序各自实现 | 置信度校准与人为接受标签 |
| ReviewTask / Feedback | 都要指定角色、留下不可覆盖决定 | 共享契约与追加记录；页面分 Domain | Stage 7 旧队列迁移与正式 RBAC |
| 排序器 | 泵流量/扬程 vs 维修历史/故障/风险 | 暂不共享 | 第三领域是否有相同稳定语义 |

抽象打分时按出现频率、语义相似、稳定性、复用价值与复杂度成本逐项解释，不机械求总分。`PD-001`：旧泵规则执行器白名单绑定 `inquiry.*`，目前保留以避免回归，Stage 8 建小型通用 Rule Runtime + 售后字段白名单；待第二次迁移验证。`PD-002`：旧推荐以 product candidates 表达，新增 `Recommendation(options/actions/warnings/evidence/risk)` 和海川适配器，旧产品排序未搬 Core。`PD-003`：旧试点 UI 偏销售，新增启航设备视图；同一任务/反馈语义可以复用。`PD-004`：Stage 7 SQLite 未强制租户作用域，Stage 8 新存储先示范隔离，迁移与生产安全仍是债务。

## Product thesis V1 与商业检验

可检验的假设是：**工业设备企业一线销售和售后反复依赖少数专家，从授权资料与历史记录提炼带证据的内部建议，能减少重复查找与无效升级，同时把复杂问题交回专家。** 工程复用已在小型模拟切片得到支持；买方是谁、预算、ROI、销售周期、交付毛利和两个细分市场是否相同，均未被验证。不要由此宣称“万能 Agent 平台”。

| 指标 | 本次能报告 | 下次必须测 |
|---|---|---|
| Discovery→首个 Demo | 脚本可重放，不等于人日 | 实际开始/完成日、参与人时和范围 |
| Demo→Pilot / Pilot→Production | 无真实部署，N/A | 授权、接入、验收和风险门的日历时间 |
| Core 改动数与客户分支 | 新契约/执行器有改动；无 `if tenant == ...` 业务分支 | 每个新客户引入的核心改动、例外与迁移成本 |
| 质量/业务 | 合成 10/10 Top-1，未自动指导 | 真实错误成本、工程师接受/覆盖、客服处理与安全事件 |
| 平台成本 | Stage 1–8 回归可跑 | 版本兼容、回归时间、维护工时、基础设施与客服支持 |

可将 Sprint 投入**试设**为 60% 第二客户问题、25% 已验证复用、15% 债务/评估；比例随现场证据调整。下一轮优先完成真实售后 Discovery 和资料授权、SSO/RBAC 与租户隔离评审、工程师独立标注与危险建议集，再决定有限 Shadow。技术 Roadmap 按“更快给专家可信上下文和正确升级”排序，而非按组件数量排序。

当前决策：**继续模拟迭代，不进入真实 Pilot 或跨客户发布。** 下一阶段应讨论产品方向与资源组合，但不能把 Stage 8 的合成结果当成投资回报证据。
