# 启航 Discovery、As-Is 与 AI 边界

## 90 分钟模拟 Discovery

客户负责人张总希望“AI 直接告诉客户怎么修”，这只是**诉求**，不是授权或已验证的正确流程。观察对象是客服小周处理 `QH-001`：先问 QH-75 型号和序列号、查设备档案及最近维修、记录 E37、5 bar/平时 8 bar、异响和昨日日常保养，再查现行手册并请工程师判断是否需要现场处理。案例记录是为教学构造，没发生真实访谈。

| 时间 | 要观察/追问 | 证据或尚缺项 |
|---|---|---|
| 0–20 分 | 请客服从接到电话/微信到建工单完整演示；每次系统切换计时 | 本仓库仅有虚构工单，真实录屏/计时尚缺 |
| 20–40 分 | 序列号如何核实？同型号不同配置能否混用手册？ | 资产 ID、工单 ID、有效日期、保养状态需权威系统签核 |
| 40–60 分 | 工程师解释 E37 与异常声音、高温、保养后故障的差异 | 风险规则需工程师和安全负责人逐条批准 |
| 60–75 分 | 客服能说什么？何时停止远程建议、何时派工？ | 责任、升级时限、客户沟通 SOP 尚待确认 |
| 75–90 分 | 量化重复问答、误判成本、处理/派工时间与复盘机制 | 必须先真实前测，不能用本文件的模拟数代替 |

## Problem Brief 与决策地图

**待验证问题**：一线客服在确认设备和风险后，是否反复花时间查散落的工单/手册，且把本可结构化的信息重新问给售后工程师。目标不是让 AI 自主维修，而是让客服更快整理设备、症状、已知证据、未知条件，并把危险或不确定情况及时交给工程师。

```text
Service Request → 确认序列号 → 资产/保养历史 → 故障码及运行读数
                → 有效手册与安全规则 → 内部暂定下一步 → 客服/工程师审核
                → 人工客户沟通；必要时人工派工
```

| 决策 | 机器可做 | 必须由人决定 |
|---|---|---|
| 设备身份 | 精确序列号匹配；不存在/型号不一致就弃答 | 修正别名与设备档案，确认客户归属 |
| 症状抽取 | 抽取 E37、压力/温度、异响、近期保养，保留缺字段 | 核查转写错误、危险工况 |
| 证据 | 仅检索本租户、当前有效、角色可见的手册片段 | 手册/规则批准及冲突处理 |
| 下一步 | 生成有来源的内部选项和风险警告 | 安全决定、客户指导、停机/派工与最终诊断 |

原稿提到维修手册 PDF、故障码 Excel、SOP DOCX、旧手册和 FAQ；本阶段没有读取或伪造真实文件，而用带 `status/version/effective_date/owner` 的**合成 JSON 片段**演练治理。旧手册 `QH-OLD-2021` 被检索前过滤。产品资料、客户资产和实际安全阈值都不是现实技术依据。

## MVP 范围与拒绝条件

MVP 只对内部人员展示设备摘要、受控证据、下一步**待审核**选项和升级原因。序列号未知、设备型号不一致、异响、≥95°C、涉及电柜或压力容器都阻断自动客户维修指导并路由工程师；其中 E37 + 异响 + ≥95°C 触发 `SERVICE_E37_003` 的 critical 路径。`95°C` 只是虚构演练阈值，不能作为真实安全指令。规则的执行框架可共享，规则内容与责任必须归售后 Domain 和启航租户。

没有客户直达聊天机器人、自动拆机步骤、自动停机命令、自动派工、价格或保修承诺。真实案例需单独进行安全风险评估、责任归属与事故响应设计。
