# 租户边界、评估层级与平台发布门

`TenantStore.scope(tenant_id, domain)` 先核对配置中的租户/领域映射，所有 `get/list/feedback/review` SQL 都带这两个条件。`WorkItem`、资产上下文、知识、规则、Trace、建议、Eval 和审核任务以 `(tenant_id, domain, kind, id)` 为主键；写入时拒绝与当前 Scope 冲突的显式租户/领域。检索由 Scope 先取本租户文档，然后才做 `status/effective_date/allowed_roles/model/intent` 过滤，不存在“全库搜索后靠 Prompt 过滤”。测试尝试从启航读取海川保修文档、从海川读取启航 Trace/任务、跨租户请求资产历史以及跨租户审核，均应失败或返回空。

这仍只是单机教学隔离：`--tenant` 命令行参数和页面角色切换不是可信身份来源，能直接打开 SQLite 的操作者可绕过应用层 Scope。真实平台需经认证身份绑定租户、授权策略、数据库 RLS 或物理隔离、服务账号最小权限、静态/传输加密、审计与数据删除策略，并用越权测试和渗透评估验证。不能把本机测试通过解释成生产多租户安全认证。

## 三层 Eval

| 层级 | 此仓库检查 | 真实发布还缺 |
|---|---|---|
| Core | 抽取运行时、规则白名单、作用域存储、任务和反馈引用 | 可靠性、并发/竞态、权限与异常恢复 |
| Domain | Stage 4–7 外贸回归；Stage 8 的售后字段、Top-1、风险和路由 | 独立工程师标签、危险建议审查、覆盖误差和现场结果 |
| Tenant | 海川 P7-001 适配；启航 10 条合成工单、租户知识隔离、版本 | 每个客户自己的授权资料、数据门、权限与事故演练 |

运行 `python3 stage_pipeline.py all` 会按 Stage 1–8 执行；CI 另跑完整测试与关键阶段回归。`stage8.py eval --check-baseline` 的 50/50 字段、10/10 Top-1 和 0 条自动危险指导是**小型自造集的回归预期**。它们不等于真实抽取准确率、诊断命中率、维修解决率或安全 Release Gate。

```text
Core 改动 → Core Tests → 外贸回归 → 售后回归
          → 海川租户案例 → 启航租户案例 → 人工变更审查
          → 真实数据与安全门（本仓库未完成）→ 有限部署
```

配置变更、知识更新和规则发布同样走版本差异、Owner 确认、离线评估和审批，不能绕过代码发布门。新客户加入后，“复用”增加了回归面；测量真正的交付速度时要分 Discovery→Demo、Demo→Pilot、Pilot→Production，记录真实日期与负责人，而非拿原稿的 10 天/4 天示例当绩效。
