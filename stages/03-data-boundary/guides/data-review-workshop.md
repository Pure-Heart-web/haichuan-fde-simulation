# Data Review Workshop（约 120 分钟）

| 时间 | 动作 | 必须写下的决定 |
|---|---|---|
| 0–20 分 | 核对收到的资料清单、覆盖数、格式与所有者 | 哪些是原始邮件、结构化事实、上下文、文档、规则候选 |
| 20–45 分 | 对比 CP90 在技术表、销售主数据和目录中的值 | D-001 字段级冲突、批准人、生效范围、未决项 |
| 45–65 分 | 用两个订单查看同名客户与别名 | C-001 身份归并证据；歧义时停止自动关联 |
| 65–85 分 | 阅读聊天摘录与产品条件 | 将口头经验转成规则候选，标记验证状态 |
| 85–100 分 | 核对标准价格与客户特价的敏感级别 | 首版模型上下文允许/禁止清单 |
| 100–120 分 | 回读 AI Boundary、20 条评估标签及门槛 | 未验证规则、缺失文件、责任人和下轮交接 |

陈工负责技术参数与规则签阅，销售运营负责客户身份和订单，管理层负责价格权限，FDE 负责数据契约和评估口径。讨论中不因文件名带 `NEW` 或 `Final` 就判定其权威；以 Owner、批准和生效日期为准。

## 特别追问

哪一列是技术部正式批准的参数？销售表里商业字段与技术字段能否拆开？目录 2025 中 CP90 对应哪个技术版？订单别名有合同抬头或 CRM ID 吗？聊天里的“海水要 SS316”在哪些产品和环境成立？如无书面确认，规则应停留在 `candidate`，不要进入可执行生产约束。

**演练不产出真实准确率。** 20 条 Golden Dataset 用于设计评估，Stage 4 实现后再将模型预测与标签比较，报告置信区间、错误分类和复核成本。原稿的 95%/90%/0/100% 只是 Pilot 候选门槛，须在真实样本与风险评审后确认。
